# 写真カルテ機能 Phase1 ワイヤーフレーム＋操作仕様 (PHOTO_KARTE_UX_WIREFRAME_1)

作成日: 2026-09-03
前提: [[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]](UX設計) / [[PHOTO_KARTE_DB_DESIGN_1]] / [[PHOTO_KARTE_API_DESIGN_1]] / [[PHOTO_KARTE_AUDIT_1]]
ステータス: **ワイヤーフレーム＋操作仕様のみ**。8節の通り実装境界を明示する。

## 0. 本書の目的

スタッフが施術中に迷わず、最短操作でBefore/After写真を撮影できることを唯一の評価軸とする。
[[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]で確定した方針(ゴースト重ね合わせ・3段階透明度・
body_partへの角度統合・比較UXのPhase分け)を、実際の画面構成とタップ操作の単位まで
具体化する。UXの新しい方針転換は行わない(前回設計書の延長線上の具体化に徹する)。

## 1. 撮影画面

### 1-1. 画面構成(ワイヤーフレーム)

```
┌───────────────────────────────────┐
│ ✕        顔全体・正面        [施術前|施術後]  │ ← A: header
├───────────────────────────────────┤
│                                       │
│                                       │
│         ライブカメラプレビュー           │ ← B: video
│      (ゴーストがある場合は半透明で重畳)     │
│                                       │
│      ┌ ─ ─ ─ ─ ─ ─ ┐               │ ← C: 静的ガイド(常時)
│      ┊    顔の輪郭目安    ┊               │
│      └ ─ ─ ─ ─ ─ ─ ┘               │
│              +                       │ ← 中央十字線
│                                       │
├───────────────────────────────────┤
│  ゴースト: [前回|初回]   濃さ:[OFF|25%|50%]  │ ← D: ゴースト操作列
├───────────────────────────────────┤
│ [顔全体・正面✓][左45°][右45°][額][左頬]... │ ← E: 部位チップ(横スクロール)
├───────────────────────────────────┤
│               ●  シャッター                 │ ← F: シャッター
└───────────────────────────────────┘
```

### 1-2. Before / Afterの切り替え位置(A)

- ヘッダー右上に常設の`[施術前|施術後]`ピル型トグル。カメラ画面を閉じずに切替可能
  (After撮影フロー時にBeforeへ後から戻って撮り足す、逆にBefore中にうっかりAfterを
  見返す等、両方向の操作をカメラを開き直さずに行えるようにするため)。
- このトグルの状態が、これから撮る写真すべての`photo_type`を決める
  ([[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]2-1節の方針を維持。部位ごとに毎回選ばせない)。
- 写真カルテセクション(カメラを開く前の入口画面)にも同じトグルを表示し、状態はセッション中
  (同じ来店対応中)は保持する。カメラを閉じて再度開いても直前の状態を引き継ぐ。

### 1-3. 部位選択UI(E)

- ヘッダー下ではなく**シャッターの直上**(親指の可動域内、1-6節参照)に横スクロールの
  チップ列として常駐。カメラを閉じずに部位を切り替えられる。
- 選択中のチップは色反転+ヘッダー中央のラベル(A)にも部位名を表示(現在何を撮っているか
  を2箇所で確認できる、確認の二重化)。
- チップの右上に小さな状態マーク:
  - サムネイルまたは✓: この部位の「前回写真」が存在する(ゴーストが出る)
  - 空(無地): この部位はまだ一度も撮っていない(初回撮影になる)
- チップの並び順は5節の固定語彙順で固定(顔全体・正面→左45°→右45°→額→左頬→右頬→鼻→顎→
  目周り→首→その他)。表示順がセッションごとに変わらないことを優先し、「よく使う順」等の
  動的並び替えはPhase1では行わない(予測可能性を優先、迷いを減らす)。

### 1-4. カメラプレビュー(B)とゴースト表示

- `<video>`要素(ライブ映像)の上に、ゴースト画像`<img>`を`position:absolute`・
  `opacity`可変で重畳する2層構造([[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]1-4節の技術的不変条件)。
- ゴーストが存在しない部位(初回撮影)の場合、この層は非表示になり、C(静的ガイド)のみが残る。

### 1-5. OFF / 25% / 50%の切り替えUI(D)

- ゴースト操作列に3択の segmented control として配置(`[OFF] [25%] [50%]`、
  選択中がハイライト)。連続スライダーは採用しない([[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]1-3節)。
- 同じ行に`[前回|初回]`の基準切替ボタンを並べる(4節で詳述)。
- ゴーストが存在しない(初回撮影)部位を選んでいる間は、この行全体を**disabled表示**にする
  (押しても何も起きない状態を「押せそうに見える」まま放置しない)。
- 直前に選んだ濃さは端末の`localStorage`に保存し、次回このカメラ画面を開いた時の初期値にする
  (スタッフごとの好みへの追従、Phase1はサーバー同期しない)。

### 1-6. 静的ガイド(C)

- 中央十字線+顔の輪郭目安を示す薄い楕円ガイド(SVGオーバーレイ)。ゴーストの有無に関わらず
  常時表示。
- 傾きインジケーター(任意、[[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]1-5節): 標準Web API
  `DeviceOrientationEvent`でスマホの左右傾きが一定角度を超えたらガイド線の色を変える。
  実装コストが低いため、Phase1に含めるかは実装側で判断してよいがワイヤーフレーム上は
  「あってもレイアウトを崩さない」設計にしておく(C層に含める、専用スペースは確保しない)。

### 1-7. シャッターボタン(F)

- 画面下端中央〜やや右寄り(片手操作を優先、[[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]1-6節)。
- 円形・44px角以上のタップ領域。押下中は視覚的フィードバック(リング拡大等)のみで、
  他の操作(確認ダイアログ等)を挟まずシャッターを切る。

### 1-8. 撮影後の確認・撮り直し・次の部位への遷移

これが「部位選択→シャッター」の**2タップ基本操作**を守れるかの核心部分(7節で総括)。

- シャッター後、撮影したフレームを**全画面フリーズ表示**し、右下に控えめな
  `[撮り直す]`ボタンのみを出す。
- **1.5秒間操作がなければ自動的に確定**し、ライブカメラ画面へ戻る(またはAfterフロー時は
  次の未撮影部位へ自動遷移、3節参照)。**確定のための能動的なタップは不要**——これにより
  通常操作は「部位チップ(1tap)+シャッター(1tap)」の2タップのまま維持される。
- 明らかにブレている等、スタッフが**能動的に**気づいた場合のみ、1.5秒以内に
  `[撮り直す]`をタップ(+1タップ)。タップするとフリーズ表示を破棄し、同じ部位・同じ
  ゴースト設定のままライブカメラへ即座に戻る(部位選択をやり直す必要はない)。
- 次の部位への遷移:
  - **Beforeフロー**: 自動確定後はライブカメラ画面(E: 部位チップ列)に戻るのみ。
    どのチップを次に撮るかはスタッフが選ぶ(自由撮影、2-2節)。
  - **Afterフロー**: 自動確定後、チェックリスト上の**次の未撮影(○)部位へ自動的に
    切り替わる**(3節)。全て✓になった時点で完了バナーを表示する。

### 1-8-1. アップロードタイミング(R1反映・正式仕様)

シャッター〜確定までの間、**サーバーへは一切送信しない**。処理順序を以下に確定する。

1. シャッター押下時点では、`<canvas>`でキャプチャしたフレームを**ローカルのBlobとして
   保持するのみ**(1-4節のcanvasキャプチャ処理はここまで)。この時点で`POST`は呼ばない。
2. 全画面フリーズ表示+1.5秒タイマー開始(1-8節の通り)。
3a. **1.5秒経過し、かつ`[撮り直す]`が押されなかった場合**(自動確定): このタイミングで
    初めて`clientRequestId`(UUIDv4)をクライアント側で新規生成し、
    `POST /api/customers/[id]/photos`をローカルBlob付きで実行する。画面は**POSTの完了を
    待たずに**次の状態(Beforeならライブカメラ、Afterなら次の未撮影部位)へ即座に遷移する
    (ネットワーク待ちでスタッフの操作を止めない。POSTは非同期のバックグラウンド処理として扱う)。
3b. **1.5秒以内に`[撮り直す]`が押された場合**: `POST`は一切呼ばない。ローカルBlobを破棄し、
    フリーズ表示を閉じてライブカメラプレビューへ戻る(同じ部位・同じゴースト設定を維持)。
    **サーバー側には何も存在しない状態のままなので、DELETE APIを呼ぶ必要はない。**

この設計により「撮り直す」操作は常にクライアント内で完結し(通信もDB操作も発生しない)、
`commitCustomerPhoto.ts`の冪等性設計(`clientRequestId`起点)とも整合する
(1回の確定=1回の新規`clientRequestId`=1回のPOST)。

**1.5秒はPhase1の暫定値**とする。実機検証(スタッフの実際の反応速度・「撮り直す」への
気づきやすさ)を踏まえて調整可能な値として扱い、実装時はマジックナンバーではなく定数として
切り出す(値そのものの妥当性は9節の未決事項として引き続き残す)。

### 1-8-2. 通信失敗時のリカバリ(「通信失敗時にスタッフが詰まらないか」への回答)

1-8-1節3aの通り、POSTは自動確定と同時に画面遷移した**後**にバックグラウンドで実行される。
このためスタッフが失敗に気づける仕組みが別途必要になる。

- POST失敗時は**自動リトライ**(同一`clientRequestId`を使い、冪等性を利用して安全に再送可能。
  回数・間隔の具体値は9節の未決事項)を行う。
- 自動リトライも失敗した場合、当該コマ(部位チップ or チェックリスト行)に**警告バッジ**
  (例: `⚠再送信が必要`)を表示する。✓(確定)でも○(未撮影)でもない**第3の状態**として扱う。
- 警告バッジの行/チップをタップすると、(a)手動で再送信を試みる、(b)同じ部位を撮り直す、
  のいずれかを選べる小さな確認を出す。
- **スタッフは警告バッジが出ている状態でも他の部位の撮影・施術後フローへの移行を継続できる**
  (通信失敗が全体の操作をブロックしない)。写真カルテセクションを開いた際にも
  未送信・送信失敗が残っている場合はバナーで知らせ、放置されないようにする。
- ローカルBlobの保持範囲はPhase1では**メモリ上のみ**とする(アプリを完全に閉じた場合は
  再送信できず、その部位は「未撮影」のまま戻る=ブレ写真が誤って残ることはない安全側の設計)。
  IndexedDB等での永続化(アプリ強制終了後も再送信できるようにする)はPhase1.5以降で検討する
  (9節の未決事項)。

### 1-9. カメラ起動失敗時の画面(権限拒否・非対応・getUserMedia失敗) — R4反映

カメラ画面(1節)を開こうとした際、`getUserMedia`が成功しなかった場合の代替画面を
以下の3パターンで定義する。いずれも共通の基本導線
**「カメラを使用できません」→「カメラ権限を確認」→「もう一度試す」**を必須とする。

```
┌───────────────────────────────────┐
│ ✕                                     │
│                                       │
│            📷✕                       │
│        カメラを使用できません             │
│                                       │
│   ┌─────────────────────────┐   │
│   │   （状況別の案内文、下表参照）      │   │
│   └─────────────────────────┘   │
│                                       │
│        [ カメラ権限を確認 ]              │
│        [ もう一度試す ]                 │
│                                       │
│   （1-10節のfallbackを提供する場合）        │
│        [ 写真を選択して記録する ]           │
└───────────────────────────────────┘
```

| 状況 | 判定方法 | 案内文 | `[カメラ権限を確認]` | `[もう一度試す]` |
|---|---|---|---|---|
| **権限拒否**(`NotAllowedError`) | `getUserMedia`の例外種別 | 「カメラの利用が許可されていません。設定からカメラへのアクセスを許可してください」 | ブラウザ/OSの設定手順テキストを表示(プログラムから設定画面を直接開けるとは限らないため、端末別の文言出し分けが必要になる可能性あり) | 再度`getUserMedia`を呼び直す |
| **非対応**(`mediaDevices`自体が存在しない、非HTTPS等) | API存在チェック | 「この端末・ブラウザではカメラ機能を利用できません」 | 表示しない(押しても解決しないため出さない) | 表示しない(再試行しても状況は変わらないため) |
| **その他の失敗**(`NotFoundError`/`NotReadableError`等、カメラが他アプリ使用中・一時的な不調) | 上記以外の例外 | 「カメラを起動できませんでした。他のアプリがカメラを使用していないか確認してください」 | 表示しない | 再度`getUserMedia`を呼び直す(一時的な問題である可能性が高いため) |

「非対応」だけ`[もう一度試す]`を出さないのは、再試行しても状態が変わらない操作をスタッフに
提示して迷わせないため(このケースでは1-10節のファイル選択フォールバックが実質的な
唯一の代替手段になる)。

### 1-10. ファイル選択による代替撮影 — Phase1必須(推奨)

| 観点 | Phase1に含める場合 | 含めない場合(Phase1.5送り) |
|---|---|---|
| メリット | 権限拒否・非対応・カメラ使用中のいずれでも「完全に詰まる」状態を避けられる。`<input type="file" accept="image/*" capture="environment">`は`getUserMedia`のライブプレビューとは別の経路(OS標準カメラアプリ呼び出し)であるため、Web側の権限が一部制限されている状況でも動作する可能性がある | 実装スコープを最小化できる |
| デメリット | ゴースト重ね合わせ・静的ガイド・3段階透明度が一切使えない「素の撮影」になる(1〜4節の中核UXを提供できない) | カメラが使えない間、その顧客のBefore/After記録が**完全に不可能**になる。写真カルテという機能の根幹(記録を残すこと)自体が止まる |

**推奨: Phase1必須。** 理由: 本設計全体の目的は「迷わず・最短操作で**撮れること**」であり、
ゴースト等の付加価値以前に「そもそも撮れない」状態は目的達成の前提を崩す。エステサロンの
現場では端末を複数スタッフで共有する運用もありうるため、カメラ権限・使用中などの
一時的な障害が起きる可能性は無視できない。

ただし**スコープは最小限に絞る**: フォールバック画面では「撮る」ボタン1つのみを提供し、
ゴースト・透明度切替・静的ガイドは一切出さない(ネイティブのカメラUIに委ねる)。撮影後は
通常フロー(1-8-1節)と同じくローカルBlobとして扱い、`POST`のペイロード形式(WebP変換等の
クライアント側処理)は通常撮影と共通化する。これにより追加実装コストを「入力経路の分岐」
程度に抑える。

## 2. Before撮影フロー

すべて「部位チップをタップ→カメラが開く→シャッター」という同じ操作列だが、
**ゴーストの有無とバッジ文言だけ**が状況によって変わる。以下3パターンで具体化する。

### 2-1. 初回顧客(その顧客自体が来店履歴を持たない)

| ステップ | 画面状態 | スタッフの操作 |
|---|---|---|
| 1 | 写真カルテセクションを開く。全チップが無地(前回写真なし) | チップ1つをタップ(**1 tap**) |
| 2 | カメラ起動。ゴーストなし、静的ガイドのみ。バッジ「初回の記録として保存されます」 | 目視でガイドに合わせる(操作なし) |
| 3 | シャッター(**1 tap**) | — |
| 4 | 1.5秒フリーズ→自動確定→ライブカメラへ戻る | 撮り直す場合のみ+1 tap |

**基本操作: 2 tap/枚**

### 2-2. 既存顧客・前回写真あり(該当body_part)

| ステップ | 画面状態 | スタッフの操作 |
|---|---|---|
| 1 | 対象チップにサムネイル/✓表示あり | チップをタップ(**1 tap**) |
| 2 | カメラ起動。ゴースト自動表示(基準=前回、濃さ=前回選択値 or 既定25%) | ゴーストに合わせて構図調整(操作なし) |
| 3 | シャッター(**1 tap**) | — |
| 4 | 自動確定 | 撮り直す場合のみ+1 tap |

**基本操作: 2 tap/枚**(1-8節の自動確定により、前回写真ありのケースでも操作数は変わらない)

### 2-3. 既存顧客・前回写真なし(顧客自体は既存だが、その部位/角度が未撮影)

顧客全体としては初回ではない(例: 過去に「顔全体・正面」は撮っているが「左45°」は
今回が初めて)ため、2-1節とはバッジ文言を分けて誤解を防ぐ。

| ステップ | 画面状態 | スタッフの操作 |
|---|---|---|
| 1 | 対象チップは無地(この部位/角度だけ前回写真なし) | チップをタップ(**1 tap**) |
| 2 | カメラ起動。ゴーストなし、静的ガイドのみ。バッジ**「この部位は初回撮影です」**(顧客全体が初回、との混同を避ける文言) | 目視でガイドに合わせる |
| 3 | シャッター(**1 tap**) | — |
| 4 | 自動確定 | 撮り直す場合のみ+1 tap |

**基本操作: 2 tap/枚**(2-1節と操作数は同じ、UI上の文言のみ異なる)

## 3. After撮影フロー

### 3-1. 入口: Before撮影済み部位のチェックリスト

写真カルテセクション、またはカメラのヘッダートグル(A)で`[施術後]`へ切り替えると、
ライブカメラ画面が**チェックリスト画面**に置き換わる(部位チップ列(E)がチェックリストに変わる)。

```
┌───────────────────────────────────┐
│ ✕      施術後の撮影         [施術前|施術後]  │
├───────────────────────────────────┤
│  ✓ 顔全体・正面    Before ✓  After ✓      │ ← 撮影済み(緑チェック、サムネ付き)
│  ○ 顔全体・左45°   Before ✓  After ○      │ ← 未撮影(タップで即カメラ起動)
│  ○ 右頬           Before ✓  After ○      │
├───────────────────────────────────┤
│         残り2部位・[完了して閉じる]           │
└───────────────────────────────────┘
```

- リストは**この来店(`visit_id`)でBeforeを撮影した部位のみ**を対象に自動生成する
  (Beforeを撮っていない部位はこのリストに出さない=撮影対象を勝手に増やさない)。
- 行全体がタップ領域。○(未撮影)の行をタップすると、その`body_part`が確定した状態で
  即座にカメラが開く(部位を選び直す操作は発生しない=Beforeと同じ2タップ運用を維持、
  「チェックリストの行タップ(1tap)+シャッター(1tap)」)。

### 3-2. Before/Afterの取り違え防止

- `photo_type`はA(ヘッダートグル)の状態からのみ決定され、撮影のたびにスタッフが
  選択する余地を与えない(構造的防止、[[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]2-1節の踏襲)。
- Afterのカメラ画面に入る経路は**チェックリストの行タップのみ**とし、Beforeのような
  自由な部位チップ選択は提供しない。これにより「Beforeを撮っていない部位のAfterを
  うっかり先に撮ってしまう」余地自体をUI構造でなくす。
- 例外として、Beforeを撮らずAfterだけ記録したい運用(施術後だけ記録するケース)が
  実際に必要かどうかは7節末尾の未決事項とする(Phase1では**チェックリストに現れない
  部位のAfter単独撮影はUIから提供しない**、という制限付きの設計を初期案とする)。

### 3-3. 未撮影部位の表示

- ○マーカー、行全体がグレートーン(まだ完了していないことが一目でわかる)。
- 行タップで即カメラ起動(3-1節)。

### 3-4. 撮影済み部位の表示

- ✓マーカー(緑)+小さなサムネイル。行は依然タップ可能(**再撮影を許可**、
  1-8節の「撮り直す」を過ぎた後でも、施術後に見返して撮り直したいケースに対応)。
- 再タップした場合の挙動は**3-5節(R3反映・再撮影の正式ルール)**に従う。Phase1では
  「同一visit_id+body_part+photo_type」につき写真は常に最大1枚に保つ。
- 全部位が✓になった時点でチェックリスト下部に完了バナーを表示し、`[完了して閉じる]`を
  目立たせる(施術後は次の顧客対応に早く戻りたい動線を優先、
  [[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]5-2節の踏襲)。

### 3-5. 再撮影(既に確定済みの写真を撮り直す)ルール — R3反映・正式仕様

**確定ルール: 「同一visit_id + body_part + photo_type」の写真はPhase1では常に最大1枚とする。**
Beforeの自由撮影(2節)・Afterのチェックリスト撮影(3節)いずれもこの不変条件を維持する。

#### 検討した2案

| 案 | 概要 | リスク |
|---|---|---|
| A. 削除先行(タップ直後に旧写真を論理削除してからカメラを開く) | 実装は単純 | **カメラ起動失敗・通信断・スタッフの中断が発生すると、新しい写真が撮れないまま旧写真だけ消え、その部位が「未撮影」状態に後退するデータ損失リスクがある** |
| B. **確定時置換**(新しい写真のPOST成功を確認してから旧写真をDELETEする) | 1-8-1節のPOST処理に1ステップ追加するだけで実装できる | 新DELETEが失敗した場合、旧写真が一時的に残る(下記の防御ルールで実害を防ぐ) |

**採用: B案(確定時置換)。** 理由: A案は「新しい写真が確実に手元にあることを確認する前に
唯一の記録を消してしまう」設計であり、写真カルテという記録の性質上、**撮影ミス・通信断より
記録の欠落の方が深刻**という判断による。B案は「新しい写真が存在することを確認してから
古い写真を消す」ため、途中で失敗しても最悪「新旧写真が両方残る」に留まり、「どちらも
無くなる」という最悪のケースを構造的に排除できる。

#### B案の具体的な処理順序

1. スタッフがチェックリストの✓行(既に確定済み)をタップ → 「再撮影モード」としてカメラが開く。
   このとき、置換対象となる既存写真の`photoId`をクライアント側で保持しておく
   (`replaceTargetPhotoId`)。
2. 通常の撮影フロー(1-8節・1-8-1節)と全く同じ: シャッター→ローカルBlob保持→
   1.5秒フリーズ→自動確定。**再撮影モードであっても操作・タップ数は増えない。**
3. 自動確定のタイミング(1-8-1節3a)で、通常の`POST`に加えて**POST成功後に限り**
   `DELETE /api/customers/[id]/photos/[replaceTargetPhotoId]`を続けて呼ぶ(既存の論理削除
   APIをそのまま利用、DB/API変更は不要)。
4. `POST`が失敗した場合、`DELETE`は呼ばない(旧写真がそのまま代表として残る=1-8-2節の
   通信失敗リカバリと同じ扱いになる)。
5. `DELETE`が失敗した場合(POSTは成功済み): 新旧2枚が一時的に併存する。これは下記の
   防御ルールで実害を防ぐ。

#### 防御ルール(DELETE失敗時の保険、比較UI側での対処)

上記5.のケースに備え、比較・タイムライン・ゴースト取得のいずれのクエリも**「同一visit_id+
body_part+photo_typeの中で`taken_at`が最新の1件のみを採用する」**という重複排除を
クライアント側の表示ロジックに持たせる(4節・6節に適用)。これにより、仮にDELETEが失敗して
重複行が残っても表示上は常に最新の1枚だけが「代表」として扱われ、「前回vs今回が同一visit内の
重複ショットを拾ってしまう」リスクを防げる。DELETE成功時は重複自体が存在しなくなるため、
この防御ルールは「通常は効かない、失敗時だけ効く保険」という位置づけになる。

## 4. ゴースト写真の選択ルール

「同一customer」「同一body_part」は`customer_id`と5節の統合語彙`body_part`の完全一致で
判定する。**角度を`body_part`自体に統合しているため、「同一撮影ポジション」は
「同一body_part」と同一条件になる**(別列でのポジション一致判定は発生しない)。

| 撮影文脈 | reference(ゴースト)の選び方 | 優先度 |
|---|---|---|
| Before・基準=前回(既定) | 同一`customer_id`+同一`body_part`のうち`taken_at`が最も新しい1件(`photo_type`は問わない) | 既定 |
| Before・基準=初回(1タップで切替) | 同一`customer_id`+同一`body_part`のうち`taken_at`が最も古い1件 | ユーザー操作で切替 |
| Before・該当写真が0件 | ゴーストなし。基準切替ボタン自体をdisabled化(1-5節) | — |
| **After** | **同一`visit_id`+同一`body_part`+`photo_type='before'`の写真**(通常その来店で1件のみ) | **最優先**(前回visitの写真より、今日撮ったBeforeとの位置合わせを優先) |
| After・同一visit内にBeforeが無い(3-2節の例外運用を許可する場合) | 上記Beforeロジック(前回→初回→なし)にフォールバック | 保険的な扱い |

- 「前回」「初回」の判定における`photo_type`の扱い: Beforeの参照探索では`photo_type`を
  問わない(`before`/`after`/`progress`いずれも対象)。理由は、参照したいのは
  「その部位が直近どう見えていたか」であり、前回来店の`after`写真の方が`before`写真より
  現在の状態に近いことが多いため、`photo_type`で絞り込むとかえって精度が落ちる。
- Afterの参照探索**のみ**`photo_type='before'`に限定する例外ルールとする(直接比較すべきは
  「今日の施術前」であるため、`photo_type`を絞ることに意味がある)。
- **API依存(R2)**: 「初回」の取得には`taken_at`昇順のクエリが必要。既存API
  (`GET /photos`)は`taken_at DESC`固定のため、[[PHOTO_KARTE_API_DESIGN_1]]のR2追補で
  追加する`order=asc`パラメータを前提とする。**このAPI変更はまだ`route.ts`に反映していない**
  ため、実装着手前に必ず反映が必要(9節の未決事項)。
- **重複排除(R3)**: 「前回」「初回」いずれも、3-5節の防御ルール(同一visit_id+body_part+
  photo_typeで最新1件のみ採用)を適用した上で探索する。通常運用ではこの重複排除は
  「効かない」状態(そもそも重複が存在しない)だが、DELETE失敗時の異常系でも正しい1件を
  取得できることを保証するために常に適用する。

## 5. body_part / 撮影ポジション: Phase1固定語彙案

| identifier(DB格納値) | チップ表示ラベル | 角度 |
|---|---|---|
| `face_front` | 顔全体・正面 | 正面 |
| `face_left45` | 顔全体・左45° | 左45° |
| `face_right45` | 顔全体・右45° | 右45° |
| `forehead` | 額 | 正面固定 |
| `cheek_left` | 左頬 | 正面固定 |
| `cheek_right` | 右頬 | 正面固定 |
| `nose` | 鼻 | 正面固定 |
| `chin` | 顎 | 正面固定 |

| `other` | その他 | 任意(自由記述欄はPhase1では設けない) |

CHECK制約は付けない([[PHOTO_KARTE_DB_DESIGN_1]]6節の既存方針通り)。この語彙リストは
アプリ側の定数として管理する。

### 5-1. body_partに角度を永久に混在させることによる将来の問題(明記)

Phase1では上記のフラット統合案を採用するが、**この設計を将来にわたって拡張し続けることには
明確な限界がある**。以下を実装前提として認識しておく必要がある。

1. **組み合わせ爆発**: 現状「顔全体」のみ角度別3値だが、将来「左頬も正面/斜めで撮り分けたい」
   のように部分部位にも角度バリエーションを広げると、`cheek_left_front`/`cheek_left_45`の
   ように語彙が乗算的に増える。9部位×3角度=27語彙規模になると、チップ一覧(1-3節)の
   横スクロール量が増えて「見て選ぶ」という設計意図(迷わない)自体が崩れる。
2. **クエリの脆さ**: 「角度を問わずこの部位の最新写真がほしい」という要求が将来出た場合、
   `body_part LIKE 'face_%'`のような文字列プレフィックス一致に頼ることになる。これは
   `body_part`を「値の集合」として自由に運用するという既存方針([[PHOTO_KARTE_DB_DESIGN_1]]
   6節、CHECK制約なし)と矛盾し、**命名規則という暗黙のルールへの依存**を生む。将来この
   規則を知らない担当者が`face_diagonal_left`のような非整合な値を追加すると、既存の
   プレフィックス一致クエリが静かに壊れる。
3. **集計・分析の困難**: 将来admin領域で「部位別の撮影傾向」等を集計する場合、
   "部位"と"角度"が同一列に混在していると`GROUP BY body_part`だけでは目的の軸
   (部位別か角度別か)を分離できず、都度アプリ側でのパース処理が必要になる。
4. **UIの柔軟性低下**: 将来「まず部位を選び、次に角度を選ぶ」という2段階選択UIに変えたい
   場合、`body_part`が1列に統合されたままだと文字列パース→2列化のmigrationが必要になる。

**Phase1での判断**: 上記のリスクを認識した上で、**「顔全体」の3角度のみ**という限定的な
統合に留めることでリスクを抑制する(4-27通りへの拡大は現時点で計画しない)。
将来、部分部位にも角度バリエーションが必要になった時点で、`body_part`を分割し
`position`列を新設するmigrationを検討するという**明確な移行トリガー**をここに記録しておく
(「角度違いが2部位目に広がったら列分割を検討する」を目安ラインとする)。

## 6. 比較画面(Phase1)

スライダー比較・フリッカー比較は**Phase1.5として分離**し、本書のPhase1スコープには含めない
([[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]4-2節の踏襲)。

### 6-1. 画面構成(ワイヤーフレーム)

```
┌───────────────────────────────────┐
│ ✕            顔全体・正面 の比較             │
├───────────────────────────────────┤
│   [前回 vs 今回]  [初回 vs 今回]  [自由に選ぶ]  │ ← 3 chip、1つがアクティブ
├───────────────────────────────────┤
│  2026-07-10・3回目来店                        │
│  ┌─────────────────────────┐   │
│  │         写真A(上段)               │   │
│  └─────────────────────────┘   │
│  2026-09-01・6回目来店(今回)                  │
│  ┌─────────────────────────┐   │
│  │         写真B(下段)               │   │
│  └─────────────────────────┘   │
├───────────────────────────────────┤
│ タイムライン ○──●──○──○──●          │ ← 横スクロールサムネイル
│           (選択中2枚がハイライト)              │
└───────────────────────────────────┘
```

### 6-2. 上下比較(既定表示)

- 常に同一`body_part`の2枚を上下に積む(左右比較は採用しない、
  [[PHOTO_KARTE_UX_OVERLAY_DESIGN_1]]4-1節: ポートレート430px制約下では上下の方が
  1枚あたりの表示領域を確保できる)。
- 各写真の上に撮影日+来店回数(`visit_count_at`)ラベルを表示。

### 6-3. タイムライン

- 該当`body_part`の全写真を`visit_count_at`昇順で横スクロール表示するサムネイル帯。
- 通常時は「選択中の2枚がハイライトされた状態」で表示。`[自由に選ぶ]`chipを選んでいる間は
  タップで1枚目→2枚目の順に選び直せる(1枚目選択後は「1枚目を選択中」の視覚フィードバックを
  出し、2枚目タップで上下比較(6-2節)へ即座に反映)。

### 6-4. 前回/初回の切り替え

- `[前回 vs 今回]`: 上段=最新から2番目の写真(`taken_at`で2番目に新しい)、下段=最新写真。
- `[初回 vs 今回]`: 上段=最古の写真、下段=最新写真。
- 「今回」は常に「現在時点でのその部位の最新撮影」を指す(比較画面を撮影直後以外の
  タイミングで開いた場合も同じ定義)。
- chipタップだけで上下比較(6-2節)の中身が即座に確定する(タイムラインでの手動選択は不要)。

### 6-5. R2/R3反映によるクエリ前提の明記

- `[初回 vs 今回]`の「最古の写真」取得、およびタイムライン(6-3節)の古い側の表示には
  4節と同じく`order=asc`(R2追補、[[PHOTO_KARTE_API_DESIGN_1]])が必要。
- `[前回 vs 今回]`の「2番目に新しい写真」を選ぶ際は、3-5節の防御ルール(同一visit_id+
  body_part+photo_typeで最新1件のみ採用)を先に適用してから順位づけする。これを怠ると、
  DELETE失敗による一時的な重複行を「2番目に新しい写真」として誤って拾い、実質的に
  同一visitの2枚を「前回vs今回」として並べてしまうリスクがある(実装前レビューR3で
  指摘された懸念)。

## 7. 各画面のタップ数・判断ポイント(総括)

| 画面 | スタッフが見て判断すること | タップ操作 |
|---|---|---|
| 写真カルテ入口 | 施術前/施術後どちらの対応か | `[撮影]` **1 tap** |
| 部位選択(Before、E) | サムネ有無で前回写真の有無を判断 | チップ **1 tap** → カメラ起動 |
| ライブカメラ(B/C/D) | ゴースト/静的ガイドに構図が合っているか目視判断 | シャッター **1 tap** |
| 撮影後プレビュー | 明らかな失敗(ブレ等)がないか一瞬確認 | 何もしなければ**0 tap**(自動確定)。撮り直す場合のみ**+1 tap** |
| チェックリスト(After) | ○/✓で未撮影部位を判断 | 行 **1 tap** → カメラ起動 |
| 比較画面入口 | どの基準(前回/初回/自由)で見たいか | chip **1 tap** |

### 7-1. 「部位選択→シャッター」2タップの維持可否 — 結論: 維持できる

- 前回写真の有無・顧客が初回か既存か・After/Beforeいずれの文脈でも、**部位/チェックリスト行
  のタップ(1)+シャッター(1)の2タップ**で1枚を撮り切れる設計にした。
- これを可能にしている核心の設計判断は**1-8節の「撮影後プレビューを1.5秒の自動確定にし、
  確認のための能動的タップを要求しない」**という点にある。もし確認画面で常に明示的な
  `[次へ]`タップを必須にする設計だった場合、基本操作は3タップになっていた。
- 例外的に操作数が増えるのは「撮り直す」場合(+1タップ)のみであり、これは品質担保のための
  意図的なコストとして許容する(頻度が低い操作にコストを寄せる設計)。

## 10. 追加レビュー(R1〜R4反映後の再確認)

| 確認項目 | 結果 | 根拠 |
|---|---|---|
| 2タップ撮影(部位選択→シャッター)は維持できているか | **維持** | 1-8-1節のPOSTは自動確定と同時に非同期実行されるため、通常操作のタップ数に影響しない。再撮影(3-5節)も同じフロー(チェックリスト行タップ+シャッター)で完結し、追加タップは発生しない |
| Before/After取り違え防止は維持されているか | **維持**(変更なし) | `photo_type`はヘッダートグルからのみ決定される構造は今回変更していない。R1〜R4はいずれもこの構造に影響しない |
| 同一visit内で写真が重複しないか | **担保**(3-5節) | 「確定時置換(B案)」により通常運用では最大1枚の不変条件を維持。DELETE失敗という異常系のみ一時的な重複が起こりうるが、6-5節の防御ルール(最新1件のみ採用)で表示上は実害が出ない |
| 前回/初回ゴースト取得が正しくできるか | **設計上は解決、API追補の実装反映待ち** | 「前回」は既存API(降順)で取得可能。「初回」は[[PHOTO_KARTE_API_DESIGN_1]]のR2追補(`order=asc`)を前提とする。**このAPI変更はまだコードに反映していない**ため、実装着手前に必ず`route.ts`への反映が必要(9節) |
| 比較UIの「今回」が撮り直し前の古い写真を拾わないか | **担保**(6-5節防御ルール) | 「同一visit_id+body_part+photo_typeで最新の1件のみ採用」という重複排除ロジックを4節・6節の全クエリに適用することで、DELETE失敗時の一時的な重複があっても「今回」は常に最新の1枚を指す |
| 通信失敗時にスタッフが詰まらないか | **担保**(1-8-2節) | 自動リトライ+警告バッジ方式により、通信失敗が他の部位の撮影や施術後フローへの移行をブロックしない。ただしローカルBlobをメモリ保持のみとするため、アプリを完全終了すると再送信不能になる制約は残る(9節の未決事項) |
| カメラ権限拒否時にスタッフが詰まらないか | **担保**(1-9節・1-10節) | 権限拒否/非対応/その他失敗の3パターンごとに案内文とボタン表示を出し分け、非対応時に無意味な「もう一度試す」を出さない設計にした。ファイル選択フォールバック(Phase1必須)により、カメラ自体が使えない場合でも記録自体は継続できる |
