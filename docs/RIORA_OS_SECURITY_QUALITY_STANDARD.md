# Riora OS セキュリティ品質基準 v1.0

作成日: 2026-08-10
位置づけ: 本書は2026-08-10に実施した「Riora OS セキュリティ品質基準 v1.0 総合監査」の結果を正典として整理した設計書である。監査はmigrationファイル・APIコード・Reactコンポーネントの読み取りに基づく調査であり、コード・DB・設定への変更は一切行っていない。

---

## 1. 基本思想

- 自店運用における「まあいい」を、SaaS品質としてそのまま許容しない。
- 今回のセキュリティ監査は「自店の傷を直す」ことが目的ではなく、**他店へ販売できる商品としての品質検査**である。
- テナント分離は他の項目と同列に扱わない。**別格であり、単独で販売可否を左右する。**
- 判定ルール: **第1層4項目のうち1つでもCなら、総合判定C＝SaaS販売不可。**
- 今年(自店運用中)は、「自店で必要かつ将来の商品土台になるもの」を優先して対応する。
- 来年の本格マルチテナント化・法務対応は、SaaS販売前に必須の作業として別枠で扱う。
- ただし、**今年のDB設計・実装で、来年のマルチテナント化を不可能にする(作り直しを増やす)構造を新たに増やさない**ことを今年の設計判断の制約とする。

## 2. 判定基準

| 判定 | 意味 |
|---|---|
| **A** | 基準を満たしている。 |
| **B** | 概ね機能しているが、一部不足・改善余地がある。 |
| **C** | 重大な不足があり、SaaS販売基準を満たさない。 |

### 販売判定ルール

**第1層4項目(テナント分離・認証認可・RLS・秘密鍵/APIキー管理)のうち1つでもCなら、総合判定C＝SaaS販売不可とする。**

#### 3-5-補足. LINE送信アクセス制御の実装仕様(2026-08-10追記)

`POST /api/line/send`・`POST /api/line/approve`の担当外顧客アクセス防止対応にあたり、以下を仕様として定める。

- `/api/line/send`および`/api/line/approve`は、送信対象顧客について`canAccessCustomer()`によるアクセス制御を行う。
- `/api/line/approve`で`customer_id`が`NULL`のキュー項目は、一般スタッフには送信を許可せず403とする。
- `customer_id = NULL`の場合、既存の`staff.isAdmin`により管理者のみ例外的に許可する(`canAccessCustomer`が既に持つ「`isAdmin === true`なら常に許可」というルールをそのまま踏襲したものであり、新しい権限ルールを追加したものではない)。
- `customer_name`や`line_user_id`をアクセス制御の代替根拠には使用しない(いずれも表示用・送信先識別用の値であり、担当判定の正当な根拠にはならない)。
- 今回の対応では`line_send_queue`のRLS(`USING(true)`)は変更していない。RLS是正(3-3章・12章TOP10-4参照)は、別途migrationを伴う課題として引き続き残る。

## 5. 「後で足せる余地」の具体化

抽象的な「将来store_idを追加する」ではなく、実装者が迷わないよう以下を明文化する。

- 新規に作成する主要テーブルには、可能な限り最初から`store_id`列を持たせる。
- 店舗単位で一意であればよい値(例: 顧客の店舗内識別番号等)に、安易にグローバルUNIQUE制約を設定しない。
- 将来必要になった場合に`(store_id, xxx)`の複合UNIQUEへ移行できるよう、制約設計時に店舗単位の一意性を意識する。
- 固定UUID(`DEMO_STORE_ID`等)を、店舗境界そのものとして新規コードへ埋め込まない。
- UUIDの推測困難性を、テナント分離の代替として扱わない(API層の明示的なstore_idチェックが本質的な防御である)。
- 認証主体(スタッフ)と店舗所属を、将来分離できるデータ構造を維持する(現状`RequestingStaff`型にstore_idが無いことは、この観点での既知の負債)。
- store_id/tenant_idの動的解決(リクエスト元スタッフの実店舗から導出する仕組み)を、将来導入できる設計を意識する。

**ただし、今年は本格的なマルチテナント化を実装しない。** 上記はあくまで「今年の実装判断が来年の作り直しを増やさないための注意点」である。

## 7. 要配慮・センシティブ情報の内部保護基準

法的な分類(個人情報保護法上の「要配慮個人情報」に該当するか等)は本書では断定しない。

Riora OS内部基準として、以下の情報は**安全側に倒して保護対象として扱う**方針とする。

- 肌状態
- 肌悩み
- 健康状態に関係する情報
- 禁忌事項
- カルテ情報
- 音声メモ
- 音声文字起こし
- カルテ画像

> これらが個人情報保護法上の「要配慮個人情報」に該当するか等の最終的な法的分類は、販売前に法務確認を行う。

現状(3-12・6章参照)、これらの情報は保存時に暗号化されておらず、一部(禁忌事項・引継ぎノート等)はRLSが全開放状態にあるため、**内部基準として掲げる保護水準と実装が一致していない**ことを明記する。

## 13. 総合判定

**現時点: C — SaaS販売不可**

理由: 第1層4項目のうち、

- テナント分離: C
- 認証・認可: C
- RLS: C
- 秘密鍵・APIキー管理: B

であり、判定ルール(第1層4項目のうち1つでもCなら総合判定C)により、総合判定はCとなる。

なお、自店(1店舗)運用の継続自体を脅かす致命的バグは今回ほぼ発見されなかった(唯一の例外は12章TOP10-1のLINE送信権限チェック漏れ)。今回の多くのC判定は「1店舗運用では表面化しないが、店舗が2つ以上になった瞬間に破綻・漏洩する」設計であり、これは自店運用の安全性そのものへの疑義ではなく、SaaS化に向けた準備状況の評価である。
