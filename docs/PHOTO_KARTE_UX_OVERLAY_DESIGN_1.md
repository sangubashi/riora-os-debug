## 1. 撮影ガイド重ね合わせ機能

### 1-1. 基本コンセプト

カメラプレビュー(`<video>`)の上に、前回撮影した同一部位・同一角度の写真を半透明の
`<img>`レイヤーとして重ねる「ゴースト重ね合わせ」。BeforeAfter系アプリ(施術ビフォーアフター
共有アプリ)の標準機能だが、Riora OSでは**顧客記録に内蔵**されているため、写真を選ぶ手間
(アプリ間コピー等)がゼロという点が差別化ポイントになる(6節で詳述)。

```
┌─────────────────────┐
│  ● REC  正面・顔全体      │ ← 現在の部位/角度ラベル
│                        │
│   ░░░░░░░░░░░░░░░    │ ← 前回写真(半透明レイヤー)
│   ░░░ ゴースト像 ░░░    │
│   ░░░░░░░░░░░░░░░    │ ← カメラのライブ映像(下)
│                        │
│  [OFF|弱|強]   ●シャッター│ ← 3段階トグル + 撮影ボタン
└─────────────────────┘
```

### 1-2. 部位/角度ごとの前回写真選択

撮影対象を選ぶのは「部位チップ」であり、チップを選んだ時点でAPIが
`GET /api/customers/[id]/photos?bodyPart=X&limit=1`(既存の一覧APIをそのまま利用、
`taken_at DESC`で1件)を呼び、最新の同一`body_part`写真をゴーストとして自動セットする。
**スタッフが「重ねる写真」を手動で探して選ぶ操作は発生させない**(自動選択がデフォルト、
2-4節で「基準を前回→初回に切り替える」操作のみ用意する)。

### 1-3. 透明度調整

連続スライダーではなく**3段階トグル**(OFF / 弱=25% / 強=50%)を採用する。

理由: 施術中は片手・手袋・時間的制約がある状態での操作になりうる。連続スライダーは
「ちょうどいい透明度」を探る微調整コストが高く、位置合わせという本来の目的から気を逸らす。
3段階なら親指タップ1回で確実に切り替えられる。デフォルトは「弱(25%)」——ライブ映像を
隠しすぎず、輪郭合わせの手がかりとして十分な濃さ。直前に選んだ強度は`localStorage`に
端末単位で記憶し、次回起動時のデフォルトにする(スタッフごとの好みに追従、サーバー保存は不要)。

### 1-4. ガイド表示は撮影時のみ・保存画像に焼き込まない（技術的不変条件）

これは実装上、自然に満たせる設計にする:

- ゴースト画像は`<video>`要素の**上に重ねたDOMレイヤー**(`position: absolute`の`<img>`、
  `opacity`をCSSで制御)として表示するのみ。
- シャッター時のキャプチャ処理は`<canvas>.drawImage(videoElement, ...)`で**videoフレームのみ**
  を読み取る。ゴースト`<img>`レイヤーはcanvas描画の対象に一切含めない。
- したがって「焼き込まない」は追加のガード処理を要する話ではなく、**キャプチャ処理の実装が
  video要素だけを参照する限り構造的に満たされる**。実装時のレビューポイントとしては
  「canvasにゴーストレイヤーを誤って合成していないか」の1点のみ確認すればよい。

### 1-5. カメラプレビューとの位置合わせ方法

AR的な自動位置合わせ(顔検出・自動トラッキング)は**Phase1のスコープ外**とする。理由:

- 顔検出ライブラリの新規導入(MediaPipe等)は画像処理ライブラリ未選定という既存の残課題
  ([[PHOTO_KARTE_AUDIT_1]]「残る確認事項」)をさらに拡大させ、Phase1の複雑化を招く。
- エステの施術写真は医療用の精密比較(皮膚科の定点撮影装置等)ほどの機械的厳密性は不要で、
  「だいたい同じ構図」で経過が伝わればスタッフ・顧客双方にとって十分な価値がある。

Phase1は**スタッフの目視合わせ+視覚的アシスト**の3点セットとする:

1. **ゴースト重ね合わせ**(1-1〜1-3節) — 前回写真がある場合の主手段。
2. **静的グリッドガイド**(中央十字線+顔の輪郭目安の薄い楕円ガイド) — ゴーストの有無に関わらず
   常時表示。初回撮影(前回写真が無い)時はこれが唯一のガイドになる(2-3節)。
3. **水平インジケーター**(スマホの傾きが±5度を超えたら枠の色を変える等の簡易表示) —
   実装コストが低く、左右の傾きだけでも構図のブレを大きく減らせる。既存の
   `DeviceOrientationEvent`(標準Web API、追加ライブラリ不要)で実現可能。

将来、精度を上げたい場合はPhase3以降で顔ランドマーク検出による自動アライメント支援
(「もう少し右」等のガイダンス)を追加検討する余地を残すが、**今回はUX設計にも実装にも含めない**。

### 1-6. スマホでの操作性

- 全操作を**片手・親指の可動域内**に収める。シャッターボタンは画面下部中央〜右寄り
  (右利き優先だが中央寄せで両利き対応)、ゴーストトグルはシャッターの左側に横並び。
- ボタンサイズは既存アプリの他のプライマリアクション相当(44px角以上、タップミス防止)。
  `CustomerBottomSheet.tsx`が430px幅前提のため、カメラ画面もこの幅制約の中でレイアウトする
  (全画面モーダルとして開くため実際の描画幅はデバイス幅いっぱいまで使えるが、
  ボタン配置の基準は「片手操作」を優先し、横幅を無駄に使った左右分散配置はしない)。
- 部位/角度の切り替えはカメラ画面を閉じずに行えるようにする(横スクロールのチップ列を
  画面下部・シャッターの上に常駐させる)。「1部位撮ったら一旦画面を閉じて部位選択に戻り、
  また開き直す」という往復操作を避けることが、施術中の速度に直結する最重要ポイント。

## 2. 撮影フロー

### 2-1. Before / After

`photo_type`は撮影のたびにスタッフが選ぶのではなく、**フローの状態**として画面側が持つ。

- 施術開始時に写真カルテを開く → 画面上部に「施術前 / 施術後」の2状態トグルが表示される
  (デフォルトは施術前=`before`)。
- このトグルを1回切り替えるだけで、以降撮る全部位の`photo_type`が一括で`after`になる。
  部位ごとに毎回「before/afterどっち?」を選ばせる設計はミスの元なので採用しない。
- `progress`(定点観察・施術と紐付かない単発撮影)は、来店に紐づかない撮影
  (`visitId`を送らないケース、初診カウンセリング等)を選んだ場合にのみ使う別入口とする。
  通常の施術フローには登場させない。

### 2-2. 同一部位・同一角度の維持

3-2節で確定する「部位+角度を`body_part`語彙に統合する」運用により、Before撮影時に選んだ
`body_part`値(例: `face_front`)がそのままAfter撮影時の初期選択候補になる。

具体的には、施術後に「施術後」トグルへ切り替えた瞬間、画面には**その来店(`visit_id`)で
Beforeを撮った部位一覧**がチェックリストとして表示され(5-2節)、Afterがまだ無い部位が
ハイライトされる。スタッフは一覧をタップするだけで「Beforeと同じ部位・同じ角度」の
撮影画面に入れる——部位を選び直す操作自体をなくすことで、取り違えの余地を構造的に減らす。

### 2-3. 前回写真が存在しない初回時の挙動

- ゴーストレイヤーは非表示(元々表示するものが無い)。1-5節の静的グリッドガイドのみ表示。
- カメラ画面に控えめなバッジ「初回の記録として保存されます」を表示し、スタッフに
  「これが今後の比較の基準になる」ことを伝える(構図を多少なりとも意識してもらう効果を狙う)。
- 部位選択チップの表示自体は前回写真の有無に関わらず同じ(全部位が選択可能)。「前回写真あり」
  の部位にはチップに小さなサムネイル(または✓マーク)を付け、初回の部位と視覚的に区別する。

### 2-4. 「前回」ではなく「初回」を基準にする選択肢

必要——経過が長い顧客ほど「前回とはほぼ変わらないが初回からは大きく変わった」というケースが
価値の中心になるため、基準を1種類に固定すべきではない。

ただし**撮影のたびに毎回選ばせる操作にはしない**(1-2節と同じ思想: デフォルトは常に「前回」)。
カメラ画面のゴーストトグル群に、透明度3段階とは別に基準切り替えの小さいラベルボタン
`前回 ⇄ 初回`を1つ追加するだけに留める。タップすると読み込むゴースト画像が
最新1件→最古1件に切り替わる(APIは同じ一覧エンドポイントの並び順違いで対応可能、3節参照)。
撮影自体のフロー(部位選択→ゴースト表示→シャッター)は変わらない。

## 3. 写真データ設計との整合性

### 3-1. 結論: 現行スキーマ(migration未適用)で実現可能。DB変更は不要

[[PHOTO_KARTE_DB_DESIGN_1]]で確定済みの`brain_customer_photos`
(`id, store_id, customer_id, visit_id, body_part, photo_type, storage_path, taken_at,
created_by, created_at, deleted_at`)のまま、本書の機能はすべて実現できる。追加列・追加テーブル・
CHECK制約の変更は提案しない。

### 3-2. body_part / photo_type / taken_at / visit_id の使い方

| 要件 | 使うカラム | クエリ/運用方法 |
|---|---|---|
| 「同一部位・同一角度」の一致判定 | `body_part` | **角度を`body_part`の語彙自体に統合する**(下記)。DB制約ではなくアプリ層の統一語彙リストという既存方針([[PHOTO_KARTE_DB_DESIGN_1]]6節)をそのまま延長する |
| 「前回の写真」取得 | `customer_id` + `body_part` + `taken_at DESC LIMIT 1` | 既存の複合インデックス`(customer_id, body_part)`([[PHOTO_KARTE_DB_DESIGN_1]]11節)がそのまま使える。新規インデックス不要 |
| 「初回の写真」取得 | 同上 + `taken_at ASC LIMIT 1` (または`visit_id`経由で`brain_visits.visit_count_at ASC`) | 同じインデックスで昇順に変えるだけ。専用の「is_first_photoフラグ」等は不要 |
| Before/Afterペアの表示 | `visit_id` + `photo_type` | 既存の`GET /photos?visitId=X`(`photo_type`昇順で返す設計、[[PHOTO_KARTE_API_DESIGN_1]]1節)をそのまま使える |
| 経過タイムライン(初回/3回目/6回目/現在) | `visit_id`→`brain_visits.visit_count_at` | [[PHOTO_KARTE_DB_DESIGN_1]]5-1節で既に設計済みのJOINクエリをそのまま流用 |

**body_part語彙への角度統合案**(vocab拡張、CHECK制約なしのためmigration不要):

```
既存案(DB設計書6節): face_full, forehead, cheek_left, cheek_right, nose, chin, eye_area, neck, other

角度統合後の案:
  顔全体系: face_front(正面), face_left45(左斜め45°), face_right45(右斜め45°)
  部分系:   forehead, cheek_left, cheek_right, nose, chin, eye_area, neck
  その他:   other
```

「顔全体」は角度による見え方の差が大きいため角度別に3値へ分割し、頬・額等の部分部位は
基本正面固定で撮る想定のため角度を持たせない(運用を複雑にしすぎない)。この語彙リストは
将来Phase4の肌マップ細分化時と同様、**アプリ側の定数ファイルとして管理し、追加はmigration不要**。

### 3-3. reference_photo_id列は追加しない(判断とその理由)

「どの前回写真をゴーストとして使ったか」をDB上に記録する設計(`reference_photo_id`列の
追加)も検討したが、**Phase1では見送る**。理由:

- ゴースト表示は撮影を補助する**一時的なUIの状態**であり、撮影後に永続化すべき記録ではない。
  「後からどの写真を参照したか知りたい」というニーズが実際に出た場合でも、
  `body_part`一致・`taken_at`が近い過去の写真を検索すれば実務上は十分再現できる。
- [[PHOTO_KARTE_DB_DESIGN_1]]で確定済みのスキーマを変更しないことを本書全体の設計方針とする
  (API設計書が「migration設計へ進んでよい」と結論した前提を崩さない)。
- 将来、比較UXの利用ログ・改善分析等で本当に必要になった場合は、独立した追記可能な設計
  (別テーブル`brain_photo_view_logs`等)として後日追加すればよく、`brain_customer_photos`
  本体には影響しない。

### 3-4. 新しいDB変更が必要になるとしたら何か(参考、今回は提案しない)

上記の通り今回は不要という結論だが、将来的に必要になりうる変更を参考として記録する
(**設計だけの提示であり、migrationは作成しない**):

- `body_part`の角度統合(3-2節)が実運用で粒度不足と分かった場合、`angle`列を別途追加する案
  (`text`, nullable, CHECK制約なし)。ただし3-2節の統合案で当面は十分と判断する。
- 比較UXの利用実績を分析したくなった場合の`brain_photo_view_logs`(閲覧・比較イベントの記録、
  写真本体テーブルとは分離)。

## 4. 比較UX

### 4-1. 5パターンの評価

| パターン | 実装コスト | 施術中スタッフへの価値 | 用途 |
|---|---|---|---|
| **左右比較**(横並び) | 低 | 中(ポートレート430pxでは1枚が狭くなる) | 汎用 |
| **上下比較**(縦並び) | 低 | **高**(ポートレート固定の当アプリと最も相性がよい。1枚あたりの横幅をフルに使える) | 汎用・**Phase1の既定表示** |
| **スライダー比較**(ドラッグでワイプ) | 中〜高(clip-path+ドラッグ操作の実装) | 中(見栄えが良く顧客説明・SNS的訴求に強いが、施術中の速い確認には上下比較で足りる) | 顧客への説明・魅せる場面 |
| **重ね比較**(トグル/フリッカー、同一フレームで2枚を切替表示) | 低〜中 | **高**(微妙な変化を見つけやすい。実装コストの割に効果が大きい) | 経過の微差確認 |
| **タイムラインから任意の2枚選択** | 中(横スクロールUI+選択状態管理) | 高(比較の入口として必須。「前回/初回」ボタンの土台にもなる) | 比較対象の選定そのもの |

### 4-2. Phase別実装優先度

**Phase1(必須)**:
- タイムラインストリップ(その部位の全写真を`visit_count_at`順にサムネイル横スクロール表示)
  — これ自体が「比較したい2枚を選ぶ」入口を兼ねる。
- 上下比較(選んだ2枚をポートレート画面に縦積み表示、それぞれに撮影日・来店回数のラベル)。
- 「前回 vs 今回」「初回 vs 今回」のワンタップ chip(4-3節)。

**Phase1.5(低コスト・高価値、Phase1直後の追加候補)**:
- 重ね比較(トグル/フリッカー)。同じ2枚の画像を同一の`<img>`位置に重ねて`opacity`を
  `0↔1`で切り替えるだけの実装で済み、スライダーよりも実装コストが低いわりに
  「変化に気づきやすい」という価値が高い。

**Phase2以降(磨き込み)**:
- スライダーワイプ比較。顧客に見せる場面(接客中の説明、将来的な顧客共有機能)での訴求力は
  高いが、施術中スタッフの実務速度には必須ではないため優先度を下げる。

### 4-3. 「初回 vs 今回」「前回 vs 今回」のワンタップ導線

比較画面の最上部に、部位選択に連動した3つのchipを常設する:

```
[ 前回 vs 今回 ]  [ 初回 vs 今回 ]  [ 自由に選ぶ ]
```

- 「前回 vs 今回」「初回 vs 今回」は3-2節のクエリ(`taken_at DESC/ASC LIMIT 1`)をそのまま
  叩いて即座に2枚を確定し、上下比較を表示する。**タップ1回で結果が出る**ことを最優先する。
- 「自由に選ぶ」を選んだ場合のみ、タイムラインストリップが展開しスタッフが手動で2枚選択する
  (Phase1の必須要件である「タイムラインから任意の2枚選択」はここに実装する)。

## 5. Salon Rioraでの最短操作フロー(フェイシャル施術)

### 5-1. 具体的な画面遷移・タップ数

```
[施術前]
1. CustomerBottomSheet → 「写真カルテ」セクション → [撮影]ボタン           (1 tap)
2. 部位チップから対象を選択(例: 顔全体・正面)                              (1 tap)
   → カメラ画面が開く。前回写真があれば自動でゴースト表示(弱25%)
3. ゴーストに合わせてシャッター                                            (1 tap)
   → 保存後、自動で次の部位候補(未撮影の部位)がハイライトされ、
     画面を閉じずに部位チップ列から次を選べる
4. 必要な部位を2〜3繰り返す(顔全体・気になる部位1〜2箇所、が実運用の目安)
5. [完了]で撮影画面を閉じる                                                (1 tap)

→ 1部位あたり実質2タップ(部位選択+シャッター)。前回写真への位置合わせは
  自動表示されたゴーストに目視で合わせるだけで、追加の操作は発生しない。

[施術後]
1. 写真カルテセクションを再度開く → [施術後]トグルへ切替                    (1 tap)
   → その来店でBeforeを撮った部位のチェックリストが表示される
2. チェックリストの未撮影(After)部位をタップ                               (1 tap)
   → Beforeと同じbody_part・同じゴースト基準でカメラが開く
3. シャッター                                                              (1 tap)
4. Before撮影分だけ繰り返し、全部埋まったら自動的に「完了」表示

→ Before/After取り違えの心配なく、施術後は「チェックリストを埋めるだけ」の作業になる。
```

### 5-2. 進捗チェックリストUI

撮影中、常に「今回の来店でどの部位が埋まっているか」を可視化する:

```
顔全体・正面     ✓Before  ○After
顔全体・左45°    ✓Before  ○After
右頬            ✓Before  ✓After
```

- ○(未撮影)をタップすると即座にその部位・角度のカメラ画面が開く(2-2節のフロー本体)。
- 全て✓になったら自動的に「本日の撮影完了」バナーを表示し、撮影画面を閉じるまでの
  誘導を減らす(施術後は次の顧客対応に早く戻りたいスタッフの動線を優先)。

## 6. 競合(BeforeAfter等)分析を踏まえたRiora OSの立ち位置

| 観点 | 一般的なBeforeAfter系アプリ | Riora OSでの狙い |
|---|---|---|
| ゴースト重ね合わせ | 定番機能、多くが搭載 | 同等機能を搭載(1節)。差別化点にはしない(コモディティ機能) |
| 写真の呼び出し | アプリ内の独自ライブラリから手動選択 | **顧客詳細画面から自動で「その顧客のその部位の前回写真」が出てくる**(1-2節)。選ぶ手間がゼロ。これは独立アプリでは原理的に出せない優位性 |
| Before/After管理 | 手動でペア作成・タグ付け | `visit_id`に紐づけて**来店記録と自動連動**(2-1節・5節)。施術記録・顧客カルテと同じ画面内で完結する |
| 経過タイムライン | 撮影日ベースが中心 | **来店回数(`visit_count_at`)ベース**の経過表示が可能([[PHOTO_KARTE_DB_DESIGN_1]]5-1節)。「3回目の施術でどう変わったか」がエステの現場感覚に近い軸で見える |
| 顧客への共有・スライダー比較の華やかさ | 強い(SNS投稿前提のアプリも多い) | Phase1ではスコープ外。**「高機能にすることが目的ではない」という今回の要件と整合**させ、まずは施術記録としての実用性(4節Phase1)を固める |

**結論**: Riora OSの競争力は「単体の写真比較機能の高度さ」ではなく、**顧客記録・来店記録との
自動連動によって『選ぶ・探す』操作が消えていること**にある。本設計は一貫してこの1点
(前回写真は自動で出てくる、Before/Afterは自動でペアになる、基準切替以外はワンタップで完結する)
を軸にしている。

## 7. 未決事項・要ユーザー判断

- [ ] 3-2節の角度統合語彙案(`face_front`/`face_left45`/`face_right45`)の最終確定。
      特にRiora実際のフェイシャル施術で「正面+左右斜め45°」の3角度運用で十分か、
      現場のオペレーションに即した角度・部位リストの確認が必要。
- [ ] 1-3節の透明度3段階(OFF/25%/50%)の初期値・刻みが現場感覚に合うか(実機で要検証)。
- [ ] 1-5節「AR自動位置合わせはPhase1スコープ外」という判断への同意。
- [ ] 4-2節のPhase分け(上下比較→フリッカー→スライダーの順)への同意。特にスライダー比較を
      後回しにする判断(施術中の実務速度優先、見栄え・顧客提示価値は次点)でよいか。
- [ ] 5節のBefore/After撮影フロー(トグル1つで全撮影のphoto_typeが決まる設計)が
      実際の施術動線(部位ごとに前後で椅子の向き・照明が変わる等)と齟齬がないか。
